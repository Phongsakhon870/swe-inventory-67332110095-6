# Spec: ฟีเจอร์แจ้งเตือนสต็อกต่ำ และรายงานมูลค่าสต็อก

## 1. เป้าหมาย (Goal)
เพิ่มความสามารถให้ระบบ Inventory Management System สามารถแจ้งเตือนผู้จัดการเมื่อสินค้าใดมีจำนวนคงเหลือต่ำกว่าเกณฑ์ขั้นต่ำ (Threshold) และให้ผู้จัดการสามารถดูรายงานมูลค่าสต็อกรวมแยกตามหมวดหมู่สินค้าได้อย่างถูกต้องและแม่นยำ

---

## 2. User Story

| รหัส | User Story |
|---|---|
| **US-01** | As a พนักงานคลังสินค้า, I want บันทึกการรับและจ่ายสินค้าพร้อมอัปเดตสต็อกทันที, so that สต็อกในระบบสะท้อนจำนวนจริงในคลังสินค้า |
| **US-02** | As a ผู้จัดการ, I want รับการแจ้งเตือนทันทีเมื่อสินค้าใดต่ำกว่า threshold, so that สามารถสั่งซื้อสินค้าเติมคลังได้ทันก่อนของหมด |
| **US-03** | As a ผู้จัดการ, I want ดูมูลค่ารวมของสินค้าในสต็อกแยกตามหมวดหมู่, so that สามารถนำข้อมูลไปใช้ตัดสินใจและวางแผนด้านการเงินได้ |
| **US-04** | As a ผู้จัดการ, I want ตั้งค่า threshold แจ้งเตือนขั้นต่ำเฉพาะรายสินค้าได้, so that สินค้าหมุนเวียนเร็วหรือสินค้าสำคัญได้รับการเตือนอย่างเหมาะสม |
| **US-05** | As a ผู้ดูแลระบบ, I want เลือกและเพิ่มช่องทางการแจ้งเตือน (Email, SMS) ได้อย่างยืดหยุ่น, so that รองรับการส่งข้อความผ่านหลายช่องทางตามต้องการ |

## 3. Acceptance Criteria (Given-When-Then)

### AC ของ US-01 (บันทึกรับ/จ่ายสินค้า)
```gherkin
Scenario: บันทึกรับสินค้าเข้าคลัง
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อกเดิม 10 เมตร
  When พนักงานบันทึกรับเข้า 15 เมตร
  Then สต็อกคงเหลือกลายเป็น 25 เมตร
  And บันทึกประวัติรายการรับสินค้าสำเร็จ

Scenario: จ่ายสินค้าเมื่อสต็อกไม่เพียงพอ
  Given สินค้า "เบรกเกอร์ 30A" มีสต็อกคงเหลือ 5 ชิ้น
  When พนักงานพยายามบันทึกจ่ายออก 10 ชิ้น
  Then ระบบปฏิเสธการจ่ายสินค้าและแจ้งข้อผิดพลาดว่าสต็อกไม่เพียงพอ
  And สต็อกคงเหลือยังคงเป็น 5 ชิ้นเท่าเดิม ไม่มีการหักออก
```

### AC ของ US-02 (แจ้งเตือนสต็อกต่ำ)
```gherkin
Scenario: จ่ายสินค้าจนสต็อกต่ำกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 8 เมตร
  Then สต็อกคงเหลือ 12 เมตร
  And ระบบส่งการแจ้งเตือนถึงผู้จัดการว่าสต็อกต่ำ

Scenario: จ่ายสินค้าโดยสต็อกยังสูงกว่า threshold
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 50 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 10 เมตร
  Then สต็อกคงเหลือ 40 เมตร
  And ระบบไม่ส่งการแจ้งเตือน

Scenario: จ่ายสินค้าจนสต็อกเท่ากับ threshold พอดี (Edge Case)
  Given สินค้า "สายไฟ 2.5 sq.mm" มีสต็อก 20 เมตร และ threshold = 15
  When พนักงานบันทึกจ่ายออก 5 เมตร
  Then สต็อกคงเหลือ 15 เมตร
  And ระบบไม่ส่งการแจ้งเตือน (เนื่องจากแจ้งเตือนเฉพาะกรณีคงเหลือ < threshold เท่านั้น)
```

### AC ของ US-03 (รายงานมูลค่าสต็อกแยกหมวดหมู่)
```gherkin
Scenario: คำนวณมูลค่ารวมแยกตามหมวดหมู่ที่มีสินค้า
  Given มีหมวดหมู่ "Electrical" มีสินค้า A (จำนวน 10 ชิ้น ชิ้นละ 100 บาท) และสินค้า B (จำนวน 5 ชิ้น ชิ้นละ 200 บาท)
  And หมวดหมู่ "Tools" มีสินค้า C (จำนวน 2 ชิ้น ชิ้นละ 500 บาท)
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then ระบบแสดงมูลค่าหมวดหมู่ "Electrical" รวมเป็น 2,000.00 บาท
  And ระบบแสดงมูลค่าหมวดหมู่ "Tools" รวมเป็น 1,000.00 บาท
  And ยอดรวมมูลค่าสินค้าคงคลังทั้งหมดเท่ากับ 3,000.00 บาท

Scenario: หมวดหมู่ที่ไม่มีสินค้าคงเหลือในสต็อก (สต็อกเป็น 0)
  Given มีหมวดหมู่ "Safety" แต่ไม่มีสินค้าคงเหลือในระบบ (จำนวนเป็น 0)
  When ผู้จัดการเรียกดูรายงานมูลค่าสต็อก
  Then มูลค่าสต็อกของหมวดหมู่ "Safety" ต้องแสดงเป็น 0.00 บาท
```

### AC ของ US-04 (ตั้งค่า threshold รายสินค้า)
```gherkin
Scenario: ปรับเปลี่ยน threshold เฉพาะรายการสินค้า
  Given สินค้า "ท่อร้อยสายไฟ" มีค่า threshold เริ่มต้นเป็น 10
  When ผู้จัดการตั้งค่า threshold ใหม่สำหรับสินค้านี้เป็น 25
  Then threshold สำหรับสินค้านั้นต้องเปลี่ยนเป็น 25
  And เมื่อสต็อกลดลงเหลือ 20 ระบบต้องส่งสัญญาณเตือนสต็อกต่ำทันที
```

### AC ของ US-05 (แจ้งเตือนหลายช่องทางพร้อมกัน)
```gherkin
Scenario: ส่งการแจ้งเตือนผ่านหลายช่องทางที่ลงทะเบียนไว้
  Given ระบบได้ลงทะเบียนช่องทางแจ้งเตือน Email และ SMS
  When สินค้ามีสต็อกคงเหลือต่ำกว่า threshold
  Then ระบบต้องส่งข้อความแจ้งเตือนผ่านทั้ง Email และ SMS พร้อมกัน
```

> **การตรวจสอบตาม Checklist MASTER:**
> - **M (Measurable):** จำนวนสต็อก มูลค่าเงิน และเงื่อนไขการแจ้งเตือนระบุเป็นตัวเลขชัดเจน
> - **A (Achievable):** ทำได้จริงด้วย In-Memory Data Structures และ Object-Oriented Design
> - **S (Specific):** ระบุชื่อสินค้า ค่าตัวเลข และเงื่อนไข `< threshold` ชัดเจน ไม่คลุมเครือ
> - **T (Testable):** สามารถเขียน Unit Test ตรวจสอบ Output ได้ทันที
> - **E (External observable):** ตรวจสอบได้จาก Console Output (`print`) และ Return values
> - **R (Relevant):** ตรงกับความต้องการของผู้ใช้งานทั้งพนักงานและผู้จัดการ

## 4. In Scope / Out of Scope

### In Scope
1. การบันทึกรับ/จ่ายสินค้า และการตรวจสอบสต็อกในหน่วยความจำ (In-Memory)
2. การตรวจสอบเงื่อนไขสต็อกต่ำ (`current_quantity < threshold`) และส่งการแจ้งเตือน
3. การจำลองส่งการแจ้งเตือนหลายช่องทาง (Email, SMS) ผ่านการแสดงผลทาง Console (`print`) ตามรูปแบบที่กำหนด
4. การคำนวณและสรุปรายงานมูลค่าสต็อกแยกตามหมวดหมู่และมูลค่ารวมทั้งหมด
5. การออกแบบโครงสร้างตามหลัก SOLID และ Design Patterns (Factory Pattern, Observer Pattern)

### Out of Scope
1. การส่ง Email (SMTP) หรือ SMS Gateway ผ่านเครือข่ายภายนอกจริง
2. ระบบ Authentication และ Authorization (การล็อกอิน/จัดการสิทธิ์ผู้ใช้งาน)
3. การเชื่อมต่อฐานข้อมูลภายนอกแบบถาวร (Persistent Database เช่น MySQL/PostgreSQL) โดยในแล็บนี้ใช้ In-Memory
4. ส่วนติดต่อผู้ใช้แบบกราฟิก (Web UI / Desktop GUI)

## 5. Functional Requirements (FR)

| รหัส | ความต้องการเชิงหน้าที่ | สอดคล้องกับ Story |
|---|---|---|
| **FR-01** | ระบบต้องอัปเดตจำนวนสต็อกทันทีหลังทำรายการรับหรือจ่ายสินค้าสำเร็จ | US-01 |
| **FR-02** | ระบบต้องตรวจสอบจำนวนสต็อกคงเหลือก่อนจ่าย และปฏิเสธการทำรายการหากจำนวนไม่เพียงพอ | US-01 |
| **FR-03** | ระบบต้องส่งการแจ้งเตือนทันทีเมื่อจำนวนสต็อกคงเหลือลดลงจนต่ำกว่า threshold (`< threshold`) | US-02 |
| **FR-04** | ระบบต้องคำนวณมูลค่าสต็อกแยกตามหมวดหมู่และคืนผลลัพธ์เป็น Dictionary `{หมวดหมู่: มูลค่า}` | US-03 |
| **FR-05** | ระบบต้องรองรับการกำหนด threshold เฉพาะรายสินค้า และมีค่าเริ่มต้นของระบบ (Default Threshold) | US-04 |
| **FR-06** | ระบบต้องสามารถส่งการแจ้งเตือนไปยังผู้รับผ่านทุกช่องทางที่ลงทะเบียนไว้ได้พร้อมกัน | US-05 |

## 6. Non-Functional Requirements (NFR)

| รหัส | มิติ (Dimension) | ความต้องการเชิงคุณภาพ (วัดผลได้) |
|---|---|---|
| **NFR-01** | Performance | ฟังก์ชันรายงานมูลค่าสต็อกสำหรับสินค้า 1,000 รายการ ต้องประมวลผลเสร็จสิ้นภายใน 1.0 วินาที |
| **NFR-02** | Maintainability | สามารถเพิ่มช่องทางแจ้งเตือนใหม่ (เช่น Line, Webhook) ได้โดยไม่ต้องแก้ไขคลาส Business Logic เดิม (Open/Closed Principle) |
| **NFR-03** | Reliability | หากช่องทางการแจ้งเตือนช่องทางใดช่องทางหนึ่งขัดข้อง ต้องไม่ทำให้ Business Logic การตัดสต็อกหรือช่องทางแจ้งเตือนอื่นล้มเหลว |
| **NFR-04** | Testability | โค้ดทุกโมดูลต้องสามารถเขียน Unit Test ทดสอบแยกจากกันได้อย่างอิสระ 100% |

## 7. Design Notes
- การแจ้งเตือนต้องแยกออกจาก Business Logic ของสต็อกสินค้าอย่างเด็ดขาดตามหลัก Single Responsibility Principle (SRP)
- ใช้ Observer Pattern โดยให้ `InventoryService` ทำหน้าที่เป็น Subject คอยกระจายข่าวสารไปยัง `StockObserver`
- ใช้ Factory Pattern (`NotifierFactory`) สำหรับสร้าง Notifier ตาม Channel ที่ระบุ
- ใช้ Dependency Injection ในการส่ง Observer/Notifier เข้าสู่ระบบ เพื่อลด Coupling ตามหลัก Dependency Inversion Principle (DIP)
